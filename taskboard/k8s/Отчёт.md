# Отчёт: запуск Taskboard в Kubernetes (minikube)

Taskboard — трекер задач из прошлого задания: фронтенд на React, который в контейнере раздаёт nginx, бэкенд на Node.js и Express и база данных
PostgreSQL. В этом задании приложение запущено в однонодовом кластере minikube. Все манифесты лежат в папке `k8s`, а скрипт `k8s/setup-killercoda.sh`
готовит окружение: ставит kubectl и minikube, запускает кластер, собирает и загружает образы и создаёт секрет с паролем базы.

## Сборка и загрузка образов

Для бэкенда и фронтенда используются многоэтапные Dockerfile. Бэкенд на первом этапе компилируется из TypeScript, а в итоговый образ попадают только
скомпилированный код, миграции и production-зависимости. Фронтенд собирается Vite в статические файлы, которые затем копируются в образ с nginx.
Образы получают теги с версией, `taskboard-backend:1.0.0` и `taskboard-frontend:1.0.0`, чтобы было понятно, какой именно релиз запущен.

В задании упомянуты два способа доставить локальный образ в minikube, и в проекте использованы оба — каждый для своего сервиса. Кластер запущен с
параметром `--container-runtime=docker`, потому что первый способ работает только с Docker внутри minikube, а по умолчанию minikube использует
containerd.

Образ бэкенда собирается прямо внутри кластера. После команды `eval $(minikube docker-env)` консольный клиент docker работает с Docker-демоном
minikube, и `docker build` кладёт образ сразу туда, где его ищет Kubernetes, — без копирования и без реестра.

Образ фронтенда собирается обычным Docker на машине вне кластера, а затем загружается в minikube командой `minikube image load
taskboard-frontend:1.0.0`. Этот способ не зависит от среды выполнения кластера и подходит, когда образ уже собран заранее.

В манифестах указано `imagePullPolicy: Never`: кластер берёт только образы, которые уже лежат внутри него, и не пытается скачать их из Docker Hub, где
их нет.

## Какие абстракции Kubernetes использованы

Namespace `taskboard` отделяет все ресурсы приложения от остального кластера, поэтому их удобно смотреть и удалять одной командой.

ConfigMap хранит обычные настройки: `backend-config` содержит порт, уровень логов, адрес, порт и имя базы, размер пула соединений, а `frontend-config`
— порт nginx и адрес бэкенда. Secret `taskboard-db` хранит логин и пароль базы. Он не лежит в репозитории, а создаётся скриптом подготовки командой
`kubectl create secret generic` со случайным паролем, поэтому секреты не попадают в открытом виде в код. Контейнеры получают настройки как переменные
окружения через `envFrom`, ровно так, как приложение читало их и раньше.

PostgreSQL запущен как StatefulSet с одной репликой. Это контроллер для приложений с состоянием: под получает постоянное имя `postgres-0`, а данные
хранятся в PersistentVolumeClaim на 1 ГБ, который создаётся из `volumeClaimTemplates`. Если под перезапустится, он подключит тот же том и данные
сохранятся. Для базы есть headless Service `postgres` без собственного IP-адреса: DNS-имя `postgres` указывает прямо на под базы.

Миграции базы выполняет Job `migrate` — одноразовая задача, которая запускает под, доводит работу до конца и завершается. Его init-контейнер сначала
ждёт, пока PostgreSQL начнёт принимать подключения, затем основной контейнер из образа бэкенда применяет миграции с теми же настройками, что и у
приложения. После успешного выполнения под остаётся в статусе `Completed`, а при ошибке Job повторяет попытку до четырёх раз.

Бэкенд и фронтенд запущены как Deployment. Deployment создаёт ReplicaSet, а тот поддерживает нужное число одинаковых подов: если под упадёт, вместо
него появится новый. Бэкенд по умолчанию работает в двух репликах, фронтенд — в одной, и обе цифры меняются командой `kubectl scale`. Стратегия
обновления задана явно: `RollingUpdate` с `maxSurge: 1` и `maxUnavailable: 0`. При выходе новой версии сначала поднимается один новый под, и только
когда он готов, удаляется старый, поэтому приложение не остаётся без работающих реплик.

У пода бэкенда есть init-контейнер `wait-for-migrations`. Он запускается из того же образа и ждёт, пока в базе будут применены все миграции из папки
`migrations`, и только после этого стартует само приложение. Так бэкенд никогда не начнёт работать со старой схемой базы, даже если все манифесты
применены одновременно.

Для всех контейнеров настроены пробы. Readiness-проба определяет, можно ли направлять на под трафик: бэкенд отвечает на `/readyz` успехом, только если
есть связь с базой. Liveness-проба проверяет, что процесс жив, и при зависании Kubernetes перезапускает контейнер. Перед остановкой пода бэкенда
выполняется короткая пауза `preStop`, чтобы под успел исчезнуть из списка адресов сервиса, а затем приложение корректно завершается по сигналу
SIGTERM. Для каждого контейнера указаны запросы и лимиты ресурсов, чтобы приложение помещалось в небольшой кластер.

Service `backend` типа ClusterIP даёт бэкенду постоянный внутренний адрес и распределяет запросы между всеми его репликами. Service `frontend` типа
NodePort открывает фронтенд на порту 30080 узла кластера. Чтобы открыть интерфейс из браузера в Killercoda, используется `kubectl port-forward` на
этот сервис.

## Как сервисы взаимодействуют между собой

Браузер открывает фронтенд: запрос через port-forward или NodePort приходит в Service `frontend`, а он передаёт его одному из подов nginx. nginx
отдаёт статические файлы React-приложения, а все запросы, начинающиеся с `/api`, пересылает по адресу из переменной `BACKEND_URL`, то есть на
`http://backend:3000`.

Имя `backend` внутри namespace разрешает DNS кластера: оно указывает на Service `backend`, а тот распределяет запросы между готовыми подами бэкенда.
Поды, которые ещё запускаются или уже останавливаются, не проходят readiness-пробу и запросов не получают. Бэкенд не хранит состояние в памяти,
поэтому любой его под может обработать любой запрос, и число реплик можно менять в любой момент.

Бэкенд и Job миграций подключаются к базе по имени `postgres` и порту 5432 из ConfigMap, с логином и паролем из Secret. Это имя указывает на headless
Service, а через него — на под `postgres-0` из StatefulSet, данные которого лежат на постоянном томе.

Порядок запуска обеспечивается без ручных действий. Все манифесты применяются одной командой `kubectl apply -f k8s/`, после чего зависимости
выстраиваются сами: Job ждёт готовности базы и применяет миграции, поды бэкенда ждут окончания миграций и только потом стартуют. Фронтенд не зависит
от состояния бэкенда при запуске: Service `backend` существует сразу, поэтому nginx успешно разрешает его имя, а запросы начинают проходить, как
только поды бэкенда станут готовы.

## Запуск

Сначала готовится окружение: `bash k8s/setup-killercoda.sh`. После этого приложение запускается и масштабируется так:

```bash
kubectl apply -f k8s/
kubectl get pods
kubectl scale deployment backend --replicas=3
kubectl scale deployment frontend --replicas=2
kubectl port-forward --address 0.0.0.0 svc/frontend 8080:80
```
